# Decisions

## Local starter and costs

- One Python CLI and one local SQLite writer per ledger. Start with SOL/USDC by mint and integer units. The example opens with 100 simulated USDC. Paper settlement is atomic so its pending amount is zero. A bounded or continuous run uses only walletless quotes and dummy inventory.
- The starter used keyless Jupiter quotes, local CPU and disk, and no paid provisioning. Walletless requests share the provider’s keyless limit. At a one-minute interval a continuous process makes up to roughly 1,440 mark requests per day plus a request on each actionable signal. Keep service spend outside trading allocation. Historical query, export, storage, RPC and any paid API costs are unmeasured. Estimate them against the actual plan and get owner authorization before provisioning. [Jupiter rate limits](https://developers.jup.ag/docs/portal/rate-limits) · [Dune billing](https://docs.dune.com/api-reference/overview/billing) · [R2 pricing](https://developers.cloudflare.com/r2/pricing/)
- Quote freshness is a local request-time bound and any returned expiry. Upstream observation lag, wallet-conditioned route availability, actual platform/venue fee treatment by route, priority/signature fees, rent, impact at size, landing delays and missed fills need measurement. The fixed fee allowance and adverse-price floor are starter assumptions. The 0.1 SOL mark is a probe extrapolated to inventory, with size-dependent liquidity unmeasured. Treat synthetic fixtures as ledger evidence. Verify embedded fee treatment before calibrating a research cost model.
- The paper loss cap gates additional risk. A price gap can cross the cap between marks. The first valid mark of a UTC day uses the last valid equity as its opening value. After missing data, the recorded equity is the last valid figure until fresh marking resumes. The local decision ledger uses a config hash, with exact experiment config captured separately. Keep the initial approval gates in [[Research]] frozen before evaluating actual data.

## Evidence at bootstrap

- **paper** Synthetic replay verifies a round trip and balances. Offline tests check caps, pause and restart. On 2026-11-22 a keyless paper tick recorded a usable Jupiter mark at a local quote age of 219 ms and held at the starting balance. The separate keyless quote returned 7.023897 USDC expected and minimum output for a 0.1 SOL input. Jupiter reported 2 bps of fee and 0 bps of slippage. A funded-wallet route and execution remain untested.
- **shadow** No execution-quality evidence. Collect timestamped fresh quotes and measure hypothetical execution availability, delays and failures before asking for a funded pilot.
- **live** No funded evidence. After-cost profitability is unmeasured.

## MCP after the paper loop is stable

Start with local read-only tools for status, positions, recent decisions and market snapshots. Add `propose_trade` only after reviewing its schema and trust boundaries. Require pair and mint addresses, buy/sell direction, proposed maximum size in atomic input units, evidence timestamp, expiry and rationale. Validate and bound fields, assign a durable proposal ID and deduplicate retries. Default to paper. Refresh the quote, compute the allowable size from current state, rerun all deterministic controls, and return accept/reject with a reason and any accepted size. Keep wallet keys, raw signing, direct orders, limit writes and live-mode control outside the MCP surface. Treat all tool inputs as untrusted data. Use Jupiter’s documentation MCP as a developer reference. [MCP tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) · [Jupiter documentation MCP](https://developers.jup.ag/docs/ai/mcp)

1. **Replay and paper.** Run independently on each PC with local credentials and no wallets. Use forward paper and collect shadow evidence before asking to fund.
2. **Approval per proposal.** The owner separately authorizes a small live pilot and confirms each MCP proposal in a trusted local approval path. Rebind approval to fresh evidence, exact intent bounds and expiry, then rerun deterministic controls. One owner and process hold signing access to a dedicated low-balance wallet.
3. **Optional automatic operation.** Only for a tested approved strategy or a narrow AI proposal policy. AI auto-accept requires separate wallet-owner opt-in in local config, expiry, its own mint allowlist, lower spend caps and a trade-rate limit. Every proposal goes through the same deterministic risk code as a rule signal. Approve model changes before using them and keep rollback available.

## Live adapter requirements

- Verify the current Jupiter `/order` and `/execute` contract and the local Solana signing library at implementation time. Decode the returned transaction. Check the intended input and output mints, exact amount, minimum proceeds, expected signer, recipients and fee bounds. Limit the first pilot to routes whose behavior and reconciliation can be verified.
- Persist the unique intent, pre-submission state and reserved budget, route request ID where supported, expiry or block-height boundary, and the signature or other supported submission identifiers before sending. Pending amounts continue to count against available cash, risk and exposure. A timeout is ambiguous. Keep the reservation and keep reconciling using route identifiers, expiry and confirmed chain data. Confirm balances and executed amounts before releasing a reservation or granting another intent. Exclude routes that cannot be resolved reliably.
- Exercise restarts, duplicate signals, cap checks, pause, stale quotes and ambiguous submissions with fixtures before funding. A hard pause blocks new submissions while reconciliation continues. The owner uses a separate personal wallet for website trades. For an exceptional manual trade on the bot wallet, pause, resolve pending trades, then reconcile balances, positions and limits before resuming. To stop, pause, reconcile every pending swap, and agree on how to hold or unwind open positions.
